# 기능·비기능 요구사항

## 제품 목표와 사용자

딱지원핏은 사업을 설명하는 쉬운 답변을 받아 신청할 지원사업과 준비 자료를 확인하고, 공식 양식에 맞는 문서 작성으로 연결한다. 선정 결과를 보장하지 않는다.

고객은 예비·초기 창업자와 지원사업 제출을 준비하는 사업자다. 운영자는 상품·주문·콘텐츠 성과를 관리하는 승인된 BCC 관리자다. 외부 시스템은 공고 제공자, Supabase Auth, AI 제공자, Groble 결제, Upstash Redis다.

| N03 | 데이터 일관성  | 월 문서 revision 비교와 SET을 같은 Redis Lua 실행에서 처리. 성공·충돌 동시 요청 검사                                                         |
| N04 | 장애 명시      | 저장소 누락·실패를 503으로 반환. 메모리나 가짜 0으로 자동 대체하지 않음. UI 입력 유지                                                        |
| N05 | 입력 경계      | JSON 본문 최대 16KB, 실재 날짜, 안전 정수, 음수·소수·출처 매출 초과·임의 필드 차단                                                           |
| N06 | 시간·금액 의미 | KRW 정수, Asia/Seoul 기준 날짜. 확인일 포함. 월 결제 주문에 대한 환불 차감; 회계 순이익으로 표시하지 않음                                    |
| N07 | 접근성·반응형  | 입력 label, 키보드 사용, 오류 alert, 최소 44px 버튼, 모바일 단일 열·표 자체 가로 스크롤                                                      |

| N09 | 운영 성능 목표 | 동일 리전 기준 운영 API p95 1초 이하를 부하 검증 목표로 둔다. 아직 실서비스 부하 측정값은 아님                                               |
| N10 | 관측·복구      | 오류 코드는 고정하고 입력·토큰 로깅 금지. Redis 지속성/백업은 운영 계정 설정 확인 필요. 백업 RPO 24시간·복구 RTO 4시간은 제안 목표로 실증 전 |

| N12 | 기능 격리      | 새 `/operations`·`/api/operations`·`lib/operations` 경로로 추가. 기존 주문·작성 API 의미를 변경하지 않음                                     |

## 핵심 범위 결정

수동 확인값을 서버에 보존하는 운영 모듈부터 구현한다. 기존 주문 원장의 `registeredAt`·상태만으로 정확한 실결제액과 환불액을 계산하지 않는다. 페이지 진입용 `complete_payment` 이벤트를 매출 원본으로 사용하지 않는다. 실제 금액·중복 이벤트·취소 상태·캠페인 연결이 검증된 후 자동 집계기를 추가한다.

신규 마이크로서비스·신규 로그인 시스템·신규 결제 시스템은 도입하지 않는다. 한 Next.js 서비스에서 도메인 계산과 저장소를 분리하고, 필요한 지점에 어댑터를 추가한다.
