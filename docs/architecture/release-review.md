## 판단 기준과 8개 관점

## 수정의 계약과 한계

- 기존 Redis 키와 응답의 주된 형태를 유지한다. 결제 처리에는 상품별 `gp:ordergrant:<order>:word/presentation` 표시를 추가한다. 묶음을 발표 쪽에서 먼저 연결한 경우에도 새 Word 권한을 한 번만 연결하며 기존 발표 바인딩·동의를 보존한다. 과거 데이터에서 부분 발급 여부가 불명확하면 새 권한을 추정 발급하지 않고 확인이 필요하다.
- Redis Lua는 현재 단일 데이터베이스의 원자적 실행을 전제로 한다. 결제 취소·사용 처리에는 계정 키를 찾아 접근하는 스크립트가 있으므로 Redis Cluster로 옮길 때는 키 배치 설계를 다시 해야 한다. 운영 EVAL/키 접근 권한 확인이 필요하다.
- 리드 저장은 Redis와 Postgres 사이의 분산 트랜잭션이 아니다. DB 성공 후 완료 표시 실패 또는 응답 유실에는 중복 가능성이 있다. 실제 저장 성공은 200으로 알리되 `deduplicationPending`과 로그를 남긴다. 영구 유실 방지와 정확히 한 번 저장을 혼동하지 않는다.
- 과거에 이미 소진이 풀린 주문, 잘못 삭제된 이용권, 저장 없이 남은 리드 완료 표시, 부분 수집으로 잘못 종료된 공고는 이 코드 수정만으로 복구되지 않는다. 운영 원장·수집 근거 대조가 필요하며 이 작업에서 고객 데이터나 운영 키를 수정하지 않았다.
- 요청 ID는 관리자 API 응답과 로그의 연결용이다. 새 알림 채널·대시보드·상시 모니터링을 배포한 것은 아니다.

## 잔여 위험과 배포 전에 반드시 할 일

1. **동일 후보의 Preview 검증:** 운영과 분리된 저장소에서 Google 관리자/일반 계정/비로그인 경계를 확인하고 관리자 저장·재조회·409 충돌·503 장애를 실행한다. QA_MODE·OPS_LOCAL_MODE·테스트용 우회 설정이 운영에서 꺼져 있는지 확인한다.
2. **결제 원장과 공급자 계약 대조:** 실제 샌드박스 또는 합의된 검증 환경에서 Word·묶음·발표 결제, 재구매, 중복 이벤트, 취소와 지연 완료, 서로 다른 공고의 동시 시작을 확인한다. 판매자의 취소 요청·취소 완료 이벤트 구분과 주문번호 문자열 보존을 확인한다. 이미 영향받은 과거 주문·리드의 대조/복구 계획을 마련한다.
3. **저장소 권한·복구:** 배포 Redis에서 필요한 EVAL·키 접근이 허용되는지 확인하고 월별 운영 기록/주문 원장 백업의 복구를 시험한다. 반환할 이전 배포와 데이터 복구 절차를 기록한다. 휴면 큐·공고 캐시는 활성화 전에 각 배포·권한·부하 관문을 별도로 통과시킨다.
4. **관측과 알림 수신:** operations 5xx·결제 처리 실패·리드 insert/finalize 실패·수집 실패를 집계한다. 실패를 주입해 실제 담당자에게 알림이 도착하고 요청 ID로 추적되는지 확인한다. 로그 존재만으로 알림 운영 완료를 선언하지 않는다.
5. **실사용 출력·UI:** 느린 네트워크에서 월 전환·오류·재시도와 입력 보존, 실제 Office에서 PPTX·PDF·DOCX를 확인한다. 이번 서버/함수 검사를 브라우저 입력 지연이나 실제 유료 AI E2E로 확대하지 않는다.

현재 `npm audit --omit=dev`는 image-size 및 상위 pptxgenjs의 High 2개를 보고한다. [ICNS 취약점](https://github.com/advisories/GHSA-w3rx-r6r6-pgpr), [JXL/HEIF 취약점](https://github.com/advisories/GHSA-5p2g-fcmc-qvqq)은 확인 시 패치 버전이 제시되지 않았다. 실제 제품 export에서 서버 생성 PNG만 들어가는 경계와 설치된 PptxGenJS의 파서 미사용을 확인했다. 취약점 해소로 표시하지 않으며, 임의 이미지 업로드·외부 이미지 URL을 허용하기 전에 의존성 교체/패치와 별도 검증이 필요하다.

유지보수 측면에서 Chat의 수천 줄·다수 독립 상태는 남아 있다. 이번에는 실제 회귀를 최소 수정했다. 본문·근거·검수·발표의 버전 상태를 분리하는 후속 작업은 저장·복구 계약 테스트를 기준으로 진행하며, 최종 심사 중 전체 UI를 다시 작성하지 않는다.

## 근거와 재현

```sh
npm run test:release
npm run test:release:integration
npm run test:guards
npm run check:architecture
npx tsc --noEmit
npm run build
```

첫 명령은 외부 유료 서비스를 호출하지 않는 단위·계약 검사다. integration은 [로컬 확장 실험 환경](scale-verification.md)의 고정 loopback Redis 26379와 Postgres 25432, 테스트 역할 및 `infra/scale/jobs.sql`이 필요하다. 과거 결함 증거 3개는 Git 커밋 `e2ee1f1`을 읽으므로 해당 이력이 있어야 한다. 운영 연결 문자열을 받지 않는다. 해당 SQL·큐는 이 실험 환경에서 검사했으며 실제 앱의 작업 큐를 활성화하지 않았다. 테스트는 자체 가상 계정·주문과 임시 큐를 사용한다.

통합 명령의 최초 제한 환경 실행은 loopback `EPERM`과 Docker 소켓 권한 때문에 실패했다. 승인된 로컬 연결 권한으로 재실행해 전체 통과했다. 최종 빌드도 제한 환경에서 진행이 멈춰 중단한 뒤 승인된 로컬 빌드 권한으로 통과했다. 이 환경 차이를 제품 회귀 실패 또는 통과로 숨기지 않았다.
