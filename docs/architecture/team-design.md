# 4인 엔지니어링 검증 — 설계 결정

2026-09-17. 사용자의 명시적 요청으로 Architect(root), Implementation Engineer, 독립 Reviewer, SRE/Optimizer가 별도 에이전트로 참여한다. 이 문서는 설계 기준이며 최종 통과 여부는 최종 검증 문서에서 판정한다.

## 범위와 책임

대상은 직전 성능 개선 4개와, 그 개선을 검토하는 과정에서 발견된 공고 마감 필터 비용이다. 기존 원본 저장소와 작업본의 미커밋 변경을 보존한다. 운영 배포·운영 DB 변경·실결제·유료 AI 호출·브라우저 렌더링은 이번 검증 범위에서 제외한다. 브라우저는 사용자가 서버 측정부터 완료하도록 선택했다.

| 역할 | 독립적으로 판단할 것 | 변경 소유권 |
|---|---|---|
| Architect | 실제 전체 호출 경로, 계약 보존, 우선순위, 수정 범위와 trade-off | 설계·최종 검증·변경 범위 기록 |
| Implementation Engineer | 설계가 실제 호출 계약을 충족하는지, 실패·경합 경계 | 제품 4개 파일 + openFilter.ts, performance.test.mjs |
| Reviewer | 기존/수정 코드 대조, 인증·권한·가변 객체·날짜·캐시 불변식의 반례 | 독립 team-review.test.mjs, reviewer 보고서 |
| SRE/Optimizer | 성능 수치의 재현성·범위·모의/실제 I/O 구분, 운영 한계 | 측정기·측정 보조 코드·SRE 테스트·결과·보고서 |

구현 담당의 자체 테스트 통과가 Reviewer 승인을 대신하지 않는다. SRE도 과거의 개선율을 그대로 승인하지 않는다. 수정 이후 제품 해시가 바뀌면 해당 검토와 검증을 다시 요청한다.

## 설계 기준

1. 인증: 성공한 같은 Request/토큰에 한해 최대 5초 신원 검증 공유. 다른 요청은 재검증, 헤더 변경·실패·5초 경과는 재조회. 사용자 편집 metadata로 관리자 권한을 만들 수 없음. 결제 상태는 계속 별도 조회.
2. 추천: 지역·업력 제외 조건, 신규 소스/지역 노출 보장, 결과 순서, 입력 불변성을 유지. 계산 재사용을 위해 추천 규칙을 바꾸지 않음.
3. 공고 조회: 현재 fromRow에서 쓰는 10개 컬럼을 모두 유지. 기존 필터·정렬·limit·AbortSignal·오류 계약 보존. 운영 인덱스 적용은 기존 실제 실행 계획이 확인되기 전까지 후보로 유지.
4. 공개 캐시: fresh/stale 상한과 lease 소유권, 실패 backoff, 반환 데이터 복제, 원천 single-flight 유지. 데이터 승격 시 localUntil을 모든 성공 분기에서 동일하게 제한.
5. 마감 판정: Asia/Seoul 날짜 기준, 마감 당일 포함, null 상시 포함 유지. 캐싱하는 것은 날짜 formatter 설정뿐이며 오늘 날짜/판정 결과는 전역 캐시하지 않음.

## 독립 검토에서 되돌린 문제

### T-01 — 측정 범위 누락과 공고별 formatter 생성

Architect가 `fetchOpenPrograms → isStillOpen → kstToday` 경로를 읽어 기존 매칭 벤치마크 앞단에 매행 Intl.DateTimeFormat 생성이 있음을 발견했다. SRE는 제품을 수정하지 않은 상태에서 고정 날짜·3,000행·부산 프로필로 실제 전체 함수를 실행하여 formatter 2,400개/요청과 약 61ms를 확인했다. 직전 성능표의 `matchByButtons` 시간은 이 비용을 포함하지 않았다.

**결정:** `openFilter.ts`의 formatter를 모듈당 한 번 생성해 재사용한다. 매 호출 새 Date를 평가하고 기존 함수 서명은 유지한다. 한 요청의 날짜 문자열을 고정하는 대안은 더 적은 날짜 연산을 할 수 있지만, KST 자정에 걸친 호출의 기존 판정 의미를 바꾸므로 이번 최소 수정에서는 선택하지 않는다. 모듈 로딩 비용 1회와 formatter 메모리 유지가 trade-off다.

승인 조건: KST 자정 전후·당일/과거/미래/null 판정, 같은 프로세스 다음 날짜의 결과 갱신, 추천 출력 동일. 실제 전체 경로의 프로필별 p95가 팀 검토 시작 기준보다 30% 이상 감소해야 한다. 진단용 mock의 개선 수치를 제품 개선 수치로 사용하지 않는다.

### T-02 — 단일 혼합 벤치마크의 설명력 부족

SRE는 기존 매칭 표가 지역 필터를 타는 부산/경기와 지역 판정을 우회하는 전국 프로필을 혼합한 단일 실행임을 지적했다. 예전 수치는 해당 구성에 한정해 유효하며 운영 전체 개선율이나 각 프로필의 p95를 뜻하지 않는다.

**결정:** 기존 JSON을 보존하고 새 팀 측정기를 만든다. 프로필별 raw samples, 워밍업, 교차 순서의 최소 3회 전후 비교, 실제 로딩한 소스·입력·출력 해시를 기록한다. 기존 4개 개선의 원본 기준과 팀 검토 시작 시점 기준을 구분한다. CPU/메모리 숫자는 측정 범위와 한계를 함께 저장한다.

### T-03 — 성공 경로 위주의 회귀 검사 보완

구현 담당과 Reviewer는 기존의 정상 호출 테스트만으로 인증 교체·취소·캐시 경합 경계를 충분히 설명할 수 없다고 판단했다. 확정된 새 제품 결함을 뜻하지 않는다.

**결정:** old 인증 실패가 새 토큰 캐시를 지우지 않는지, TTL 경과의 실제 401/관리자 강등, 같은 요청의 결제 취소 재조회, 캐시 승격 경로의 수명과 lease-lost 미승격을 독립 테스트로 재현한다. Reviewer 테스트는 구현 담당 테스트와 파일을 분리한다.

## 검증 관문

- 설계: T-01~03에 대한 구현 범위/계약/trade-off 명시.
- 구현: 승인된 변경만 적용하고 기존 작업 보존.
- 독립 리뷰: 변경 코드와 실제 호출 경로의 correctness/security/maintainability 검토. 미해결 심각 finding이 있으면 구현 단계로 반송.
- 수정 재검토: 새 마감 필터 구현과 추가 테스트를 Reviewer가 재실행.
- 최종: 제품 소스 동결 → SRE 벤치마크 → 독립 회귀 검사 → 타입/ESLint/빌드/원본 보존 확인 → 같은 해시에 대한 역할별 판정 기록.

관문 통과는 이 범위의 **로컬 코드 후보**를 뜻한다. 운영 HTTP 부하, 실제 AI/결제 E2E, 운영 관측성·알림 연결, 배포 승인을 대신하지 않는다.

## BCC 공통 팀과 프로젝트별 실행 — 승인된 운영 방식

사용자는 2026-09-17 최종 검증 후 **BCC 공통 역할·검증 절차를 재사용하고, 매 작업의 실행 범위를 프로젝트별로 고정하는 방식**으로 진행하도록 승인했다.

- BCC 공통: Architect/Implementation/Reviewer/SRE 역할, 공통 기억 원본, 인수인계 형식, 독립 검토와 재검증 절차.
- 프로젝트별: 요구사항, 저장소·작업본, DB·인증·배포 대상, 검토 대상 파일, 성능 기준과 운영 승인 범위.
- 이 작업의 실제 배정: 딱지원핏 성능 최적화 후보. 다른 홈페이지·관리자 코드는 변경 대상에 넣지 않는다.
- 향후 홈페이지나 통합 관리자 작업에도 같은 역할 구조를 재사용할 수 있지만, 해당 작업의 범위와 최신 기록을 다시 확인한다. 프로젝트별 권한·배포 대상을 자동 승계하지 않는다.
